## What we're building

A lightweight web analytics platform for small businesses. It tells an owner where visitors go on their site, where they click, where they drop off, and — when something changes — sends them a short, plain-English daily digest.

An AI agent writes the narrative. Everything else is deterministic code.

## Who it's for

Small business owners who want to run their business, not learn analytics. Plumbers, bakeries, single-location retail, solo consultants. People who will never open a funnel-exploration UI.

**Explicit non-goal:** we do not compete with GA4, Amplitude, or Mixpanel. When a customer outgrows us, we help them leave. Do not add features that only make sense for mid-market or enterprise. If a proposed feature requires a customer to *learn something* to use it, it's the wrong feature.

## Hard constraints

These are not negotiable. Push back on any change that violates them.

1. **No cookies. No visitor IDs.** Visitor identity is a daily-rotating hash of `IP + user-agent + salt`. The salt rotates at midnight and the previous salt is destroyed. This is the Plausible/Fathom model.
2. **No raw event storage.** The ingest worker aggregates events into counters and drops the raw event. Nothing individually identifying is ever written to durable storage.
3. **We never sell data.** Not aggregated, not anonymized, not "for research."
4. **90-day retention on aggregates**, by default, stated publicly.
5. **One LLM call per client per day, maximum.** See "Cost discipline" below.

The honest version of the privacy promise is: *"We hold no data about your visitors as people."* Not "we hold no data" — we obviously hold aggregates. Don't let marketing copy overstate this.

No cookie banner required is a **sales feature**, not an implementation detail. Protect it.

## Cost discipline

The margin on a small-business analytics subscription is thin. The failure mode is an agent chain that costs more per client than the client pays.

- **LLMs are bad calculators.** Funnel math, delta computation, drop-off detection, click aggregation, anomaly detection — all plain code. No model involved.
- **The agent has exactly one job:** turn a computed findings object into two or three friendly sentences.
- **Use a small model** (Haiku-class) for the daily narrative. Reserve larger models for the weekly roll-up and the onboarding "here's what we found" moment, if at all.
- **`should_send` is computed before the agent runs.** If nothing moved, we never pay for a narrative.

## Pipeline

```
[tracking script]
      ↓  events
[edge ingest worker]  → aggregate → discard raw
      ↓  counters
[nightly rollup, 2am client-local]   ← pure code, no LLM
      ↓  metrics, deltas, funnel steps, anomalies vs 14-day baseline
[gate]  → should_send?
      ↓  yes                              ↓ no
[narrate]  ← ONE LLM call            [queue for weekly]
      ↓  digest object
[fan out] → email | SMS | Slack/Teams
```

## The digest object

Single source of truth. Every delivery channel renders from this. Never generate channel-specific copy separately — that's how the email and the Slack card drift apart.

```json
{
  "site_id": "abc123",
  "period": "2026-07-08",
  "headline": "Checkout drop-off jumped yesterday",
  "metrics": [
    { "label": "Visitors", "value": 412, "delta_pct": 3.2 },
    { "label": "Checkout starts", "value": 38, "delta_pct": -18.4 }
  ],
  "leak": {
    "page": "/checkout",
    "element": "#shipping-form",
    "detail": "62% of visitors who reach checkout leave at the shipping step",
    "severity": "high"
  },
  "win": {
    "page": "/pricing",
    "detail": "Pricing page traffic up 22%, mostly from search"
  },
  "narrative": "Generated by agent. 2-3 sentences, plain English, names the page.",
  "should_send": true
}
```

## Suppression rule

**A digest that arrives every day gets filtered to a folder in three weeks.** A digest that arrives only when something moved gets read.

If no metric moved more than the threshold, `should_send` is false: skip the send, batch the finding into the weekly. This is a product decision first and a cost optimization second. Don't remove it to make the dashboard look busier.

## Delivery

Nightly cron iterating clients serially is fine until several hundred sites. Don't stand up a queue on day one.

| Channel | Tool | Notes |
|---|---|---|
| Cron | Vercel Cron or scheduled worker | Fires at 2am client-local |
| Email | Resend + React Email | Templates as components |
| SMS | Twilio | One sentence + link. A2P 10DLC registration is required in the US and is slow — start it early. |
| Slack | Block Kit | JSON to a webhook |
| Teams | Adaptive Cards | JSON to a webhook |

**No image rendering in v1.** Block Kit and a decent email template look fine without a generated PNG. Satori or a headless screenshot service is a whole rendering dependency to maintain. Ship text and cards; add images only if a real customer asks.

## Onboarding

The onboarding flow is the product. If a customer can't be live in under five minutes with a single script tag, we've failed the brief. Treat friction in onboarding as a P0 bug, not a polish item.

## Frontend

Framework choice is open — React or Angular, whichever. The dashboard is deliberately simple: it renders the digest object and a small number of trend views. Resist the urge to build an exploration UI. Our customers do not explore.

## Open questions

- Drop-off detection logic against a 14-day baseline — what's the anomaly threshold, and how do we avoid firing on low-traffic noise? (Small sites have very few sessions; naive percentage deltas will be useless.)
- Weekly roll-up format for suppressed days.
- Whether GA4 import is worth supporting for customers migrating in, or whether we start their history at zero.

## Tone

The internal north star: *we're good at being small, and we'll wave goodbye when you outgrow us.* Externally, phrase it as **"Built for small. When you outgrow us, we'll help you leave."**
